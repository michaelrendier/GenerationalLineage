## Abstract

The Generational Lineage Engine is a Python toolkit for **factoral decomposition**: splitting an object into the parts it was
built from, and asking what it costs to put it back together. The objects are integers, operators, words, sequences, permutations,
processes, physical units and groups. Every tool serves one or both of two **lines**. The *decomposition line* (descent) reads an
object down; it is deductive, forward-propagating and **free**. The *emerger line* (ascent) builds an object up; it needs a choice
or an added constraint, so it reports its **cost** — and where the rebuild is genuinely undetermined it **refuses**, naming exactly
what it is owed.

The engine is built to be checked, not believed. Its 29 registered toolsets share one contract and each verifies itself; 44 named
relations are checked against computed data; the test suite runs the toolsets, the tutorials, the code blocks in this README and the
Manual, the links, and the command line; and every tutorial transcript is *generated by running the code*, so it cannot drift from
what the code does. Where an exact or exhaustive check is possible it is used instead of a sampled one, an unknown is reported as
unknown, and a claim that has not been established is labelled as such.

## Install

GenerationalLineage is pure Python 3. It needs **one** third-party package, `numpy`; everything else it imports is the standard library. It is syntax-checked for Python ≥ 3.9 and **run-tested on Python 3.12.3** (numpy 2.4.6 and 2.5.3); older Pythons have not been run.

There are two ways to install it. Almost everything is in the **Core**; the **Extended** layer adds three optional features that reach into sibling repositories.

| | Core | Extended |
|---|---|---|
| what you get | the whole engine: 27 toolsets, the lineage/emerger/ping engines, all tutorials except `90_`, all wiki pages | Core **plus** `engine.maths`, `engine.tools`, `engine.oscilloscope` (the Fermat-facet inventory, the control test, the two-panel SVG) |
| needs | this repository + numpy | this repository + numpy + three sibling repositories cloned beside it |
| `python3 -m engine --verify` | `28 toolsets ran, 28 passed, 1 skipped` | `29 toolsets ran, 29 passed, 0 skipped` |

### Core install

```bash
git clone https://github.com/michaelrendier/GenerationalLineage.git
cd GenerationalLineage
python3 -m venv .venv
source .venv/bin/activate                 # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python3 -m engine --verify
```

Expected — the last lines:

```text
27 toolsets ran, 27 passed, 1 skipped
RESULT: PASS  (core; extended layer skipped)
```

The one skipped toolset is `oscilloscope`, which belongs to the Extended layer. A skip is reported as a skip, never as a pass: on a Core install `lines.verify_all()` returns `_ok = True` and `_complete = False`.

Check what you have:

```bash

```

```text

  (expected on a plain clone — see README, 'Extended install')
```

Run everything from the repository root: the tutorials and the tests use `import engine` with the repository root on the path.

### Extended install

The Extended layer finds its three sibling repositories **in the same parent directory** as this one (`../AbrikosovTree`, and so on). Clone them side by side:

The three siblings are separate projects with their own licences; the Extended layer imports their code at run time and nothing from them is copied into this repository. What each one supplies: `AbrikosovTree` (`telperion_engine`, the 9-level Cayley–Dickson walk), `ValaQuenta` (the `h_rb_hat` maths and the box-kite maths), `FourthAgePapers` (`FermatMonster/engine`, which `telperion_engine` needs on its path). ### Troubleshooting

| you see | it means | do this |
|---|---|---|
| `ModuleNotFoundError: No module named 'numpy'` | the virtual environment is not active, or `pip install -r requirements.txt` was skipped | activate `.venv`, reinstall |
| `mode: CORE` and `extended layer absent` | the three sibling repositories are not beside this one | expected on a plain clone; do the Extended install if you want them |
| `--strict` exits with status 2 | something was skipped | you are on a Core install; that is the honest answer |
| a tutorial or test cannot `import engine` | not run from the repository root | `cd` to the repository root first |
| `--verify` prints `FAIL` for a toolset | a real failure — please open an issue with the full output | include `python3 -m engine` output and your Python and numpy versions |

### Uninstall

Delete the directory (and the `.venv`). Nothing is written outside it.

**how**: signature, worked session, guarantee, limits, provenance.

### Provenance labels

| label | meaning |
|---|---|
| **ESTABLISHED** | a published algorithm or theorem, cited, implemented here; the engine does not claim it |
| **OURS** | this project's own contract, framing, mapping or construction |
| **THEORETICAL** | stated in the framework, not established; never presented as running fact |

Status values are three-way on purpose: `HOLDS` (ran, both sides measured, they agree), `MATHS-FAULT` (ran, both sides measured, they
*disagree* — the claim is false), and `CODE-FAULT` (the check did not run — the claim is *unjudged*). A check that did not run is
never reported as passed.

## Responsible use

Several toolsets (`cipher`, `ping`, `rejewski`, `pohlig_hellman`, `stencil`, `unicity`) implement textbook cryptanalytic and
factoring methods at teaching scale. They are provided for education, research and authorised testing. They do not break modern
cryptography, and each one's page says where the method stops (a budget, an explicit refusal, a stated scope). Please use them
accordingly. Security-relevant reports: see [`SECURITY.md`](SECURITY.md).

## Known limitations

1. **The import name is `engine`.** It is generic. Use a virtual environment and do not install it beside another top-level package called `engine`.
2. **The Extended layer edits `sys.path`.** `engine.maths` puts three sibling-repository directories at the front of the import path when it loads, which can shadow a module of the same name. Core does not do this.
3. **Tested on one interpreter.** Run-tested on Python 3.12.3, Linux, numpy 2.4.6 and 2.5.3; syntax-checked for Python ≥ 3.9 only; Windows and macOS have not been run.
4. **Some tools are teaching-scale.** `re_pair` is O(n²), `jordan_chevalley` uses exact fractions, `pohlig_hellman` and `stencil` stop at a budget. They are exact where they answer and explicit where they refuse, not fast on large inputs.
5. **`logperiodic` is a numerical fit**, not an exact decomposition; its robustness to noise has not been characterised.
6. **`bio.py` is a stub.** Structural only; no medical or biological inference.
7. **`HOLDS` is not a proof of a conjecture.** The Clay-problem mappings are structural readings; the engine checks its own relations and settles no open problem. `THEORETICAL` means what it says.
8. **The curses console is not built yet** ([What's next](wiki/Whats-Next.md)).
9. **Notebooks are checked by hand, not by the test suite.** All three execute headless. Only toolsets with a notebook (`hyper_linear`, `equation_space`, firing plans) have one.
10. **The older Manual prose** (the Concepts pages and the core-facet chapters, moved from the original single-file README) was written progressively and audited against the engine after 1.0.0 ([Corrections](wiki/Corrections.md)); it can lag a future code change. What is generated and what is tested (every code block, every link, every transcript) is what to trust.
